# 搜索任务交叉执行功能优化

## 优化概述

根据用户反馈，对搜索任务交叉执行功能进行了以下三个关键优化：

1. **智能账户数量判断**：只有账户数量 >= 2 时才启用交叉执行
2. **登录状态预检查**：确保至少 2 个账户登录成功才进行交叉执行
3. **数据库升级脚本修复**：防止重复执行升级脚本

## 优化详情

### 1. 智能账户数量判断

#### 问题描述
原来的逻辑没有考虑账户数量，即使只有 1 个账户也会尝试交叉执行，这是不合理的。

#### 优化方案
```typescript
// 2. 检查账户数量是否满足交叉执行条件（>=2个账户）
if (accounts.length < 2) {
    log('main', '主流程', `📋 账户数量不足（${accounts.length}个），交叉执行需要至少2个账户，使用顺序执行模式`);
    return false;
}
```

#### 判断逻辑
- **1个账户**：自动使用顺序执行模式
- **2个或更多账户**：继续后续检查

### 2. 登录状态预检查

#### 问题描述
即使配置了交叉执行，如果账户登录状态不正确，交叉执行会失败或效率低下。

#### 优化方案
```typescript
// 3. 预检查所有账户的登录状态
const loginStatusResults = await checkAllAccountsLoginStatus(accounts, config);
const validAccounts = loginStatusResults.filter(result => result.isLoggedIn);

// 4. 检查有效登录账户数量
if (validAccounts.length < 2) {
    log('main', '主流程', `📋 有效登录账户数量不足（${validAccounts.length}个），交叉执行需要至少2个有效账户，使用顺序执行模式`);
    return false;
}
```

#### 登录状态检查机制
1. **浏览器实例创建**：为每个账户创建独立的浏览器实例
2. **页面访问**：访问 `https://rewards.bing.com` 检查登录状态
3. **多维度检测**：
   - 用户头像和账户信息元素
   - 注销链接
   - 积分信息
   - 活动相关元素
   - 页面标题
   - URL 参数

#### 登录流程处理
- **预检查目的**：登录状态预检查仅用于判断是否启用交叉执行模式，不影响实际执行流程
- **完整流程**：无论账户是否已登录，都会执行完整的登录→搜索流程
- **未登录账户**：未登录的账户在交叉执行模式中会正常进行登录流程
- **已登录账户**：已登录的账户会跳过登录步骤，直接进行搜索任务
- **流程保证**：确保每个账户都能完成完整的任务执行

### 3. 数据库升级脚本修复

#### 问题描述
原来的升级脚本没有检查字段是否已存在，导致每次启动都会重复执行升级。

#### 优化方案
```sql
-- 检查是否已经升级过
DO $$
BEGIN
    -- 检查字段是否已存在
    IF NOT EXISTS (
        SELECT 1 FROM information_schema.columns 
        WHERE table_name = 'bot_nodes' 
        AND column_name = 'search_cross_execution'
    ) THEN
        -- 添加搜索任务交叉执行开关字段
        ALTER TABLE bot_nodes ADD COLUMN search_cross_execution BOOLEAN DEFAULT FALSE;
        
        -- 更新数据库版本
        UPDATE db_version SET version = '2.12', updated_at = NOW() WHERE id = 1;
        
        -- 如果 db_version 表不存在，创建它
        INSERT INTO db_version (id, version, updated_at) 
        SELECT 1, '2.12', NOW() 
        WHERE NOT EXISTS (SELECT 1 FROM db_version WHERE id = 1);
        
        RAISE NOTICE 'Database upgraded to version 2.12 - Added search cross execution feature';
    ELSE
        RAISE NOTICE 'Database already upgraded to version 2.12 - Skipping upgrade';
    END IF;
END $$;
```

#### 修复特点
- **幂等性**：多次执行不会出错
- **状态检查**：检查字段是否已存在
- **版本管理**：正确更新数据库版本号
- **日志输出**：提供清晰的升级状态信息

## 执行流程优化

### 新的判断流程
```
1. 检查配置是否启用交叉执行
   ↓ (未启用)
   使用顺序执行模式
   ↓ (已启用)
2. 检查账户数量是否 >= 2
   ↓ (< 2个账户)
   使用顺序执行模式
   ↓ (>= 2个账户)
3. 预检查所有账户登录状态
   ↓ (< 2个有效账户)
   使用顺序执行模式
   ↓ (>= 2个有效账户)
4. 启用交叉执行模式
```

## 性能优化

### 登录状态检查优化
- **并发检查**：可以同时检查多个账户的登录状态
- **超时控制**：设置合理的超时时间（30秒）
- **错误处理**：单个账户检查失败不影响其他账户
- **资源清理**：确保浏览器实例正确关闭

### 内存管理
- **及时释放**：检查完成后立即关闭浏览器实例
- **异常处理**：在 finally 块中确保资源清理
- **状态缓存**：避免重复检查相同账户

## 兼容性保证

### 向后兼容
- **现有配置**：现有节点的配置不受影响
- **默认行为**：未启用交叉执行的节点继续使用顺序执行
- **API 兼容**：所有现有 API 接口保持兼容

### 渐进式升级
- **数据库升级**：支持从任意版本升级到 2.12
- **配置迁移**：自动处理配置字段的添加
- **错误恢复**：升级失败时提供清晰的错误信息

## 注意事项

### 性能考虑
- **登录检查耗时**：预检查会增加启动时间，但能避免后续执行失败
- **资源使用**：登录检查会创建临时浏览器实例
- **网络依赖**：登录检查依赖网络连接

### 错误处理
- **检查失败**：单个账户检查失败不影响整体判断
- **超时处理**：设置合理的超时时间避免长时间阻塞
- **资源清理**：确保异常情况下正确清理资源

### 监控建议
- **日志监控**：关注登录状态检查的成功率
- **性能监控**：监控预检查阶段的耗时
- **错误监控**：统计登录检查失败的原因
